# Cogrid — 多用户共享算力合作社 · 设计文档

> 项目代号：**Cogrid**（Cooperative Compute Grid）
> 日期：2026-08-15
> 状态：已确认方向，待实现

## 1. 项目定位

Cogrid 是一个开源的"算力合作社"：用户贡献闲置 CPU/GPU 算力换取贡献份额，有突发算力需求时按份额比例调用全网算力池。互惠互利，众人拾柴。

**本项目的特殊基因：为协作与中断而设计。**

- 本地开发只起"点火"作用——交付一个可运行的最小骨架，证明架构可行。
- 项目从第一天起就是开源的，任何阶段都能暂停、重启、终止。
- 半成品必须可被后来者理解、复用、改进，不浪费任何已做的工作。
- 细节需求在开发中遇到时，由 AI 能力判断自行调整，不阻塞推进。

## 2. 核心机制

### 2.1 贡献值与按比例分红

采用"按股分红"模型：

- **贡献分累积**：节点上报在线资源后，账本按 `贡献分 = 资源量(CPU核·GPU卡·GB内存) × 在线时长 × 探针成功率 × 质量系数` 持续累加。质量系数奖励稳定在线、任务成功率高的节点。探针成功率由 PoA 机制保障（见 §2.3）。
- **份额即股权**：每个用户的算力份额 = `自己贡献分 / 全网总贡献分`。
- **分红式调度**：调度器把当前池子的可用算力按份额比例分配给各用户。份额大者优先获得更多并发资源和更高调度优先级；份额小者也有基础保障，不被饿死。
- **突发支持**：用户可申请短时集中算力（如一次拉起 N 个节点跑训练）。超出自身份额的部分走"弹性池"——借用他人当前空闲份额，但优先级降级，份额主人一旦需要可抢占回收。
- **防滥用**：纯消费不贡献的用户份额趋零，只能用极有限的保障额度。不做硬性余额拦截，保持模型简单。

### 2.2 任务模型

- 任务以 Docker 镜像形式提交，附启动命令、资源需求（CPU 核数/GPU 卡数/内存/时长）、并发数。
- CPU 任务用普通 Docker runtime；GPU 任务用 `nvidia-container-runtime`。
- 调度器不关心任务语言——ML 用户用 Python，后端用户用任何语言都行。
- 支持任务超时、失败重试（可配次数）、优雅停止（checkpoint 友好）。

### 2.3 PoA 探针与算力固存

> 解决"没有消费者时无法衡量贡献、空闲算力白白溜走"的问题。类比水力发电：没人用电时水势能浪费——本机制把闲水泵回水库（固存），同时用流量计（PoA探针）证明水确实在流。

#### PoA 探针（Proof of Availability）— 解决"无法衡量"

即使全网零用户任务，挂机节点也能持续累积"已验证贡献"：

- 协调器定期（如每 5 分钟）向空闲节点发送轻量探针任务（几秒内完成的小计算）。
- 探针成功 = 证明节点真的在线、资源真实可用、愿意执行。
- 贡献分公式中引入 `探针成功率`：探针全部成功则系数为 1.0，失败/超时则按比例扣减。
- 探针任务极轻（CPU 跑一个小 benchmark、GPU 跑一次矩阵乘），不影响本地使用。
- 这使"挂机即贡献"成为可验证的事实，而非 unverifiable 的声明。

#### 算力固存（Compute Solidification）— 解决"算力浪费"

当池子有空闲容量且无用户任务时，调度器自动派发"填充任务"，把算力转化成持久价值。填充任务**也算真实贡献**，产出的 artifacts 就是"固存的算力"——后续用户可直接复用，等于把今天的闲水存成明天的电。

四种固存形式（按实现优先级排序）：

| 形式 | 说明 | 存储形式 | 复用方式 |
|---|---|---|---|
| 预计算缓存 | 热门模型推理结果预存 | 结构化数据（DB/文件） | 用户查询时秒取，无需实时计算 |
| 社区模型训练 | 池化 GPU 渐进式训练一个属于全体贡献者的社区模型 | 模型 checkpoint | 用户可直接 fine-tune 或推理 |
| BOINC 志愿计算 | 接入 folding@home 等公益项目 | 上传至公益项目 | 产出公益价值，提升项目声誉 |
| 镜像预构建 | 常用任务模板的 Docker 镜像提前构建 | 镜像仓库 | 用户提交任务时直接拉取，省去构建时间 |

调度规则：用户任务始终优先于填充任务。填充任务可被随时抢占让出资源（优雅停止 + checkpoint），不影响用户任务体验。

### 2.4 算力强度可调

保护贡献者的本地使用体验：

- Agent 持续监测本地 CPU/GPU/内存占用率。
- 用户设奉献档位：**保守**（仅空闲时贡献）、**均衡**（留 30% 余量）、**激进**（留 10% 余量），或自定义百分比。
- Agent 据此动态调整上报给调度器的可用资源量。本地负载升高时自动收缩——先暂停填充任务，再必要时让出弹性用户任务，最后才让出份额内用户任务。
- 档位可实时调整，无需重启 Agent。

## 3. 系统架构

三类角色通过协调器交互：

| 角色 | 技术 | 职责 |
|---|---|---|
| 协调器 Coordinator | Python/FastAPI + gRPC | API 网关、按比例调度器、贡献值账本、任务队列、PoA 探针派发、填充任务调度 |
| 节点 Agent | Python 参考版（协议开放，后续可贡献 Go 版） | 资源上报、心跳、本地负载监测、强度档位控制、Docker 任务执行、探针响应、结果回传 |
| 客户端 | CLI + React 仪表盘 | 提交/查询任务、查看贡献榜与池状态 |

### 3.1 核心数据流

**贡献侧循环**：Agent 上报资源 → 协调器定期发送 PoA 探针 → 探针成功率回传 → 账本累加已验证贡献分 → 调度器更新各用户份额。

**消费侧循环**：用户提交任务（声明资源需求）→ 入任务队列 → 调度器按份额+弹性池匹配在线节点 → 分发任务容器到 Agent → Agent 执行并回传结果与实际用量 → 账本记录消费（影响实时占用额度，不影响贡献分）。

**算力固存循环**：调度器检测池空闲 → 派发填充任务（预计算/社区模型/BOINC/镜像构建）→ Agent 执行 → 产物存入存储 → 贡献分累加 → 用户后续可复用产物。

**抢占回收**：贡献者 reclaim 自己份额时，调度器从低优先级弹性任务和填充任务中抢占，通知 Agent 优雅停止（checkpoint），任务回队列等待重新调度。抢占优先级：填充任务 > 弹性用户任务 > 份额内用户任务。

### 3.2 通信协议

- Agent ↔ 协调器：gRPC（双向流，适合心跳+任务下发，协议定义在 `proto/` 供跨语言复用）
- 客户端 ↔ 协调器：REST（简单、易调试）

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + asyncio | 无编译、可读性强、改代码方便、上手简单 |
| 节点通信 | gRPC (grpcio) | 高效双向流，协议跨语言 |
| 调度器 | 自研加权比例调度（纯 Python） | 逻辑清晰、易改易调、无外部依赖 |
| 存储 | SQLite 起步 → 可切 PostgreSQL | 单文件零运维起步，平滑升级 |
| 任务执行 | Docker SDK + nvidia-container-runtime | 容器隔离，CPU/GPU 统一接口 |
| 前端 | React + Vite + TypeScript | 仪表盘 |
| 包管理 | uv (Python) + npm (前端) | 现代、快速 |

## 6. 为协作与中断而设计（核心约束）

这是本项目区别于普通项目的关键。以下机制确保任何阶段暂停、终止后，已做的工作可被后来者理解和接续。

### 6.1 PROJECT_STATUS.md — 活的状态看板

根目录维护一份 `PROJECT_STATUS.md`，**每次提交后更新**，内容：

- 当前阶段（点火 / MVP / 增强）
- 已完成模块清单（含完成度百分比）
- 进行中工作（谁在做、卡在哪、下一步）
- 下一个接手者应从哪里开始
- 已知问题与待决事项

新贡献者打开仓库，第一眼看这个文件就知道项目到哪了、能帮什么。

### 6.2 每次提交保持可运行

- 采用 trunk-based + feature branch，feature branch 合并前必须通过测试。
- 主分支任何 commit 都可 `make dev` 拉起完整本地环境。
- 半成品功能用 feature flag 隔离（`config.toml` 开关），不破坏整体可用性。
- 提交信息用 Conventional Commits（`feat:`, `fix:`, `docs:`, `chore:`），让 git log 本身就是项目编年史。

### 6.3 模块自包含与接口先行

- 每个模块有清晰的接口定义（Python protocol / abstract base class）。
- 接口先于实现：即使实现是 stub（`raise NotImplementedError`），接口和文档注释也要完整，让后来者知道这个模块该做什么、怎么接入。
- 模块间通过接口通信，一个模块的半成品不影响其他模块运行（依赖注入 + 运行时降级）。

### 6.4 ADR — 架构决策记录

`docs/adr/` 下每个决策一个 markdown 文件，格式：

```
# ADR-XXX: 决策标题
## 状态：已接受 / 已废弃 / 已替代
## 背景：为什么需要这个决策
## 决策：选了什么
## 后果：带来什么利弊
```

后来者不必猜"为什么这么设计"，直接读 ADR。

### 6.5 TODO 带上下文

代码中的 TODO 不只写 `# TODO`，而是写：

```python
# TODO(scheduler): 实现抢占式回收，当前只支持弹性池降级。
# 下一步：在 scheduler.preempt() 中加份额主人优先级判断。
# 参考：docs/specs/2026-08-15-cogrid-design.md §2.1 抢占回收
```

### 6.6 文档与代码同步

- 每个模块目录有 `README.md` 说明职责、接口、如何测试。
- API 变更同步更新 `proto/` 和 OpenAPI schema。
- PR 模板要求勾选"是否更新了文档"。

### 6.7 开源治理

- MIT 协议，门槛最低，鼓励复用。
- `CONTRIBUTING.md` 含：环境搭建、代码规范、提交规范、如何认领任务。
- GitHub Issue 模板：bug / feature / good-first-issue 三类。
- GitHub Actions CI：lint + test 自动跑，PR 必须绿才能合并。
- 用 GitHub Projects 看板管理任务，任何阶段都能看到 backlog。

## 7. 点火范围（MVP）

本地开发交付的最小可运行骨架——证明架构可行，让社区看到愿景并开始贡献：

| # | 模块 | 点火交付内容 |
|---|---|---|
| 1 | 协调器 | 节点注册/心跳、贡献账本（含 PoA 探针成功率）、按比例调度器、任务队列、PoA 探针派发、REST API |
| 2 | Python Agent | 资源上报、本地负载监测、强度档位（保守/均衡/激进）、Docker 任务执行（CPU+GPU）、探针响应、结果回传 |
| 3 | CLI | 注册节点、提交任务、查状态、查贡献、设强度档位 |
| 4 | 仪表盘 | 池概览、节点列表（含在线/探针状态）、贡献榜、任务状态、固存产物浏览 |
| 5 | 算力固存 | 基础填充任务调度器（池空闲时派发镜像预构建+预计算缓存两类），含抢占让出 |
| 6 | 本地演示 | docker-compose：1 协调器 + 3 Agent + 仪表盘，端到端跑通（含空闲固存演示） |
| 7 | 文档 | README、架构说明、贡献指南、PROJECT_STATUS、ADR-001、ADR-002（算力固存） |

**点火验证标准**：`make dev` 后验证两条链路：
1. **消费链路**：CLI 提交一个 CPU 任务 → 调度器按份额分配到某 Agent → Agent 执行容器 → 结果回传 → 仪表盘显示贡献分变化。
2. **固存链路**：3 个 Agent 挂机无用户任务 → 调度器派发 PoA 探针 → 探针成功 → 贡献分累积 → 池空闲触发填充任务（镜像预构建）→ 产物存入存储 → 仪表盘显示固存产物。

两条链路跑通即点火成功。

后续可扩展（不阻塞点火）：社区模型训练填充、BOINC 接入、抢占式调度、Go Agent、Webhooks、多协调器集群、GPU 细粒度切分。

## 8. 错误处理与安全

- **容错**：Agent 心跳超时 → 节点标记离线 → 其上任务回队列重调度；协调器重启 → 队列与账本从 DB 恢复；任务失败自动重试（可配次数）。
- **安全**：用户 token 鉴权；任务容器资源限额（CPU/内存/超时）+ 网络隔离；GPU 任务隔离；任务镜像白名单/签名校验。
- **测试**：调度器与账本纯逻辑单测（pytest）；Agent 执行集成测；docker-compose 端到端冒烟测。

## 9. 开发体验保障

- `Makefile` 封装：`make dev`（拉起本地环境）、`make test`（全测试）、`make lint`（代码检查）、`make proto`（生成 gRPC 代码）。
- 热重载：协调器用 uvicorn `--reload`，仪表盘用 Vite HMR。
- `docker-compose.yml` 一键拉起 1 协调器 + 3 模拟 Agent + 仪表盘 + 数据库。
- 配置驱动：`config.toml` 管理所有可调参数，改行为不用改代码。

## 10. 未决事项（交由开发中 AI 判断调整）

以下细节不预先锁死，开发中按实际情况决定：

- 贡献分质量系数的具体公式（先用简单值，跑起来再调）
- PoA 探针频率与探针任务内容（先用固定 5 分钟 + 小 benchmark，后续按负载调）
- 填充任务的产物淘汰策略（存储空间有限时哪些先清理）
- 社区模型训练的目标模型与训练数据（需社区讨论决定方向）
- 弹性池抢占的具体优先级算法
- 仪表盘图表选型（先用基础组件，后续按需引入）
- GPU 细粒度切分策略（MVP 先按整卡分配）
- 多协调器共识协议（单实例起步，未来需要再加）
